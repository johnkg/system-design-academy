- Work on branch `claude/ai-depth`; one commit per task; no pull request until the user asks.

- A `sources` url that does not resolve, or uses http.
- The new area is missing from the home page, cheat sheets (`/cheatsheets/aifoundations/`) or the area filter, or a concept in it is hidden.
- Concept samples whose output differs between languages by a rounding digit.
- Pages that repeat the existing `aiml` concepts (KV cache, batching, RAG, embeddings) instead of linking them.

## Theory concepts (area `aifoundations`)

### Task 2: tokens-and-tokenization

difficulty beginner. Scenario: a support chatbot is billed per token and sometimes mangles part numbers and non-English names. Steps: text to bytes or characters; byte-pair encoding merges the most frequent adjacent pair again and again; the vocabulary is the pieces learned; the same text can be many or few tokens; limits and prices count tokens, not words; why odd strings and numbers split badly. Sources: Sennrich et al., "Neural Machine Translation of Rare Words with Subword Units" (arXiv 1508.07909). Related: `context-windows-and-long-context`, `embeddings-and-vector-search`, `llm-inference-and-kv-cache`.
**Code (yes):** train toy BPE on the fixed corpus `low lower lowest newer newest` (words end with `_`), 6 merges, print each merge as `merge N: a + b -> ab (count c)` (ties broken by first occurrence in a stated order), then print the tokens for `lowest` and `newest`. **Playground** (`TokensandTokenizationPlayground`): the same toy BPE runs in the browser over a fixed 300-character paragraph; controls `Merges` 0 to 60 (default 0), `Price per million tokens` select (default 1); outputs: tokens in the text, vocabulary size (distinct characters plus merges), embedding table size (vocabulary x 512 numbers), cost of the paragraph. Use the displayed numbers in the how list (compute them from the implementation, do not invent).

### Task 3: attention-and-transformers

difficulty intermediate. Scenario: the word "it" in "The trophy did not fit in the suitcase because it was too big" must be linked to the right noun. Steps: each token becomes a vector; queries, keys and values; scores are dot products divided by the square root of the dimension; softmax turns scores into weights; the output is a weighted sum of values; causal mask; many heads and layers with a feed-forward block, residual connections; cost grows with the square of the sequence length. Sources: Vaswani et al., "Attention Is All You Need" (arXiv 1706.03762). Related: `llm-inference-and-kv-cache`, `context-windows-and-long-context`, `how-models-are-trained`.
**Code (yes):** three tokens with fixed 2-dimensional q, k, v vectors; print the score matrix, softmax weights per row (causal mask) and the output vectors, all rounded to 3 decimals. **Playground:** controls `Sequence length` (128 to 32768, select, default 1024), `Heads` 8, `Model width` 4096; outputs: score-matrix entries per head per layer (`n x n`), multiply-adds for the scores (`n x n x width`), and how these grow when the length doubles (4x). Default `n x n` = 1,048,576 shown as `1048576`.

### Task 4: how-models-are-trained

difficulty intermediate. Scenario: why a raw pretrained model completes text but does not follow instructions. Steps: pretraining on next-token prediction with cross-entropy loss; gradient descent adjusts weights; supervised fine-tuning on instruction and answer pairs; preference tuning from comparisons (RLHF with a reward model, or direct preference optimization); what each stage changes; what training cannot add (facts after the data cutoff). Sources: Ouyang et al., "Training language models to follow instructions with human feedback" (arXiv 2203.02155); Rafailov et al., "Direct Preference Optimization" (arXiv 2305.18290); Brown et al., "Language Models are Few-Shot Learners" (arXiv 2005.14165). Related: `distributed-training-and-parallelism`, `fine-tuning-and-lora`, `model-evaluation-and-drift`.
**Code (yes):** gradient descent on loss `(w - 3)^2` starting at w=0 with learning rate 0.1 for 5 steps, printing `step, w, loss`. **Playground:** controls `Learning rate` (0.01 to 1.2, step 0.01, default 0.1) and `Steps` (1 to 50, default 20) on the same loss; outputs: final weight, final loss, and a verdict (`converging`, `oscillating`, `diverging`; a rate above 1.0 diverges for this loss). Derive every number from the iteration.

### Task 5: sampling-temperature-and-decoding

difficulty intermediate. Scenario: the same prompt gives a safe answer at temperature 0 and a creative or wrong one at temperature 1.5. Steps: the model outputs a score (logit) per token; softmax with temperature turns scores into probabilities; greedy picks the top one; top-k keeps k tokens; top-p (nucleus) keeps the smallest set whose probability reaches p; a token is drawn from what is left; why temperature 0 is only mostly repeatable in practice (floating point and batching can change results). Sources: Holtzman et al., "The Curious Case of Neural Text Degeneration" (arXiv 1904.09751). Related: `llm-caching-and-routing`, `structured-output-and-function-calling`, `hallucination-and-grounding`.
**Code (yes):** fixed logits `[4, 3, 2, 1, 0]` for tokens a to e; print probabilities rounded to 3 decimals at temperature 0.5, 1 and 2, then the tokens kept by top-p 0.9 at temperature 1. **Playground:** the same five (use eight) logits; controls `Temperature` (0.1 to 2, default 1), `Top-k` (1 to 8, default 8), `Top-p` (0.1 to 1, default 1); outputs: probability of the top token, tokens kept, entropy in bits.

### Task 6: context-windows-and-long-context

difficulty intermediate. Scenario: a contract assistant must read a 300-page document. Steps: the context window is the maximum tokens of prompt plus answer; everything the model uses must be inside it; attention cost grows with length and the KV cache grows linearly with it; a long window is not the same as using it well (the "lost in the middle" finding for the models tested); options: retrieve, summarise, chunk. Sources: Liu et al., "Lost in the Middle" (arXiv 2307.03172). Related: `llm-inference-and-kv-cache`, `retrieval-augmented-generation`, `attention-and-transformers`, `tokens-and-tokenization`.
**Code (no).** **Playground:** an example model of 32 layers, 8 key-value heads and head size 128 in 16-bit numbers (state it on the page): KV cache per token = 2 x 32 x 8 x 128 x 2 bytes = 131072 bytes. Controls `Window` select (4096, 8192, 32768, 131072; default 8192), `Prompt tokens` (default 6000), `Answer tokens` (default 1000), `Concurrent requests` (default 1). Outputs: window used (`7000 of 8192`), KV cache per request (8192-token window fully used shows `1 GiB`; derive and format), total for the requests, and `fits` or `over the window`.

### Task 7: scaling-laws-and-model-size

difficulty advanced. Scenario: a team with a fixed training budget must pick a model size and a data size. Steps: loss falls smoothly as a power law with compute, parameters and data (Kaplan et al.); training compute is about 6 x parameters x tokens; for a fixed budget, the Chinchilla paper found parameters and tokens should grow together, about 20 tokens per parameter; teams often train smaller models on far more data because every user request pays for model size; limits of the laws. Sources: Kaplan et al. (arXiv 2001.08361); Hoffmann et al., "Training Compute-Optimal Large Language Models" (arXiv 2203.15556). Related: `distributed-training-and-parallelism`, `how-models-are-trained`, `quantization-and-model-compression`. State plainly that about 20 is the ratio that paper's fits suggested, not a law.
**Code (yes):** given compute C, with D = 20 N and C = 6 N D, N = sqrt(C / 120); print N and D for C = 1e21, 1e23, 1e25 as integers in billions, rounded to 1 decimal (check the arithmetic in all three languages). **Playground:** controls `Compute budget` select (1e21, 1e22, 1e23, 1e24, 1e25 FLOPs; default 1e23), `Tokens per parameter` (5 to 200, default 20); outputs: parameters and tokens for that ratio (N = sqrt(C / (6 x ratio)), D = ratio x N), and a note when the ratio is far from 20. Quote only computed numbers.

### Task 8: quantization-and-model-compression

difficulty intermediate. Scenario: a 70-billion-parameter model does not fit on one GPU at full precision. Steps: weights are stored as numbers; fewer bits per weight means less memory and less memory traffic; rounding each weight to the nearest level with a scale; errors and outliers; 8-bit and 4-bit methods; distillation trains a small student to imitate a larger teacher; pruning removes weights; what is measured: perplexity and task scores, not size alone. Sources: Dettmers et al., "LLM.int8()" (arXiv 2208.07339); Frantar et al., "GPTQ" (arXiv 2210.17323); Hinton et al., "Distilling the Knowledge in a Neural Network" (arXiv 1503.02531). Related: `llm-inference-and-kv-cache`, `continuous-batching-and-model-serving`, `fine-tuning-and-lora`.
**Code (yes):** quantize the weights `[0.12, -0.5, 0.33, 0.9, -0.77, 0.05]` to int8 with scale = max abs / 127, print the integers, the dequantized values and the largest error, rounded to 4 decimals. **Playground:** controls `Parameters (billions)` select (7, 13, 70, 405; default 70), `Bits per weight` select (16, 8, 4; default 16), `GPU memory` (80 GB); outputs: weights memory in GB (params x bits / 8), GPUs needed for the weights alone, and a note that the KV cache and activations need more. 70 at 16 bits shows `140` GB and `2` GPUs.

### Task 9: hallucination-and-grounding

difficulty intermediate. Scenario: an assistant cites a court case that does not exist. Steps: a language model predicts plausible text, not stored facts; where wrong answers come from (missing or conflicting data, pressure to answer, no signal of uncertainty); why lower temperature does not fix it; grounding with retrieved sources and citations; abstaining; checking claims against sources; measuring the rate. Sources: Ji et al., "Survey of Hallucination in Natural Language Generation" (arXiv 2202.03629); Lewis et al., "Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks" (arXiv 2005.11401). Related: `retrieval-augmented-generation`, `guardrails-and-prompt-injection`, `model-evaluation-and-drift`, `sampling-temperature-and-decoding`.
**Code (yes):** a claim checker: given 3 source sentences and 4 answer claims, report each claim as `supported` (all its content words appear in one source sentence) or `unsupported`; print the unsupported share as a percentage. Use fixed text. **Playground:** a model with rates you set: `Questions the model knows` (default 70 percent), `Retrieval finds the answer` (default 60), `Model abstains when unsure` select Off or On (default Off). Outputs: share answered correctly, share answered wrongly with confidence, share declined; derive with: correct = known + (1 - known) x retrieved; unanswered-by-evidence = (1 - known) x (1 - retrieved); wrong = unanswered-by-evidence when abstain is Off, declined = that share when On. State on the page that these are the rates you choose, not measurements.

### Task 11: prompting-vs-fine-tuning-vs-rag

difficulty intermediate. Scenario: a legal team wants an assistant that knows its documents and writes in house style. Steps: prompting changes instructions and examples at request time; retrieval adds knowledge at request time; fine-tuning changes the model's weights; what each is good for (behaviour and format, fresh or private facts, style and skills at scale); cost and update speed; combine them; start with the cheapest. Sources: Brown et al. (arXiv 2005.14165); Lewis et al. (arXiv 2005.11401); Hu et al., "LoRA" (arXiv 2106.09685). Related: `retrieval-augmented-generation`, `fine-tuning-and-lora`, `model-evaluation-and-drift`, `how-models-are-trained`.
**Code (yes):** a function `choose(needs)` that returns advice from rules (needs: fresh_facts, private_docs, strict_format, new_style, high_volume_low_latency); print advice for 4 fixed needs sets. **Playground:** checkboxes for those 5 needs; outputs: recommended first step, what to add next, and the reason per ticked need (rule table in the script; the how list quotes the text of two results).

### Task 12: fine-tuning-and-lora

difficulty advanced. Scenario: adapting a 7-billion-parameter model to a support team's tone on one GPU. Steps: full fine-tuning updates every weight and stores gradients and optimizer state (about 16 bytes per parameter with mixed-precision Adam, from the ZeRO paper); LoRA freezes the weights and learns two small matrices A and B per adapted weight matrix so the update is B x A of rank r; trainable parameters 2 x d x r instead of d x d; adapters can be swapped per customer; quantized base (QLoRA); data quality matters most. Sources: Hu et al. (arXiv 2106.09685); Dettmers et al., "QLoRA" (arXiv 2305.14314); Rajbhandari et al., "ZeRO" (arXiv 1910.02054). Related: `how-models-are-trained`, `quantization-and-model-compression`, `model-evaluation-and-drift`, `distributed-training-and-parallelism`.
**Code (yes):** for d = 4096, r = 8: print full parameters `16777216`, LoRA parameters `65536` and the percentage `0.39`; for r = 64 print `524288` and `3.13`. **Playground:** controls `Model width d` (1024 to 8192 select, default 4096), `Rank r` (1 to 128, default 8), `Layers` (32), `Matrices adapted per layer` (1 to 4, default 2); outputs: trainable parameters, share of the 4 x d x d x layers x ... (define total attention weights as `4 x d x d x layers`), and optimizer memory (trainable x 16 bytes) compared with full fine-tuning of those matrices.

### Task 13: structured-output-and-function-calling

difficulty intermediate. Scenario: an app needs JSON it can parse, and a model that can ask the app to look up an order. Steps: ask for a format in the prompt, then validate; retry on failure; constrained decoding masks tokens that would break the grammar so the syntax is always valid; the semantic content can still be wrong; function calling: the model returns a function name and arguments, the app runs it and returns the result; validate arguments, never run what you did not allow. Sources: Willard and Louf, "Efficient Guided Generation for Large Language Models" (arXiv 2307.09702). Related: `sampling-temperature-and-decoding`, `guardrails-and-prompt-injection`, `agents-and-tool-use`, `idempotency`.
**Code (yes):** a loop with a scripted fake model that returns invalid JSON twice then valid JSON; print each attempt's result, and the final parsed value; then show a mask step: from the allowed tokens `["{", "}", "\""]` zero out the others given fixed logits and print the chosen token. **Playground:** controls `Invalid output rate` (0 to 60 percent, default 20), `Retries allowed` (0 to 4, default 2), `Method` select (Ask and validate, Constrained decoding); outputs: requests that end in valid syntax (`1 - p^(retries+1)` for validate, 100 percent for constrained), average calls per request, and a note that constrained output can be valid and still wrong.

### Task 14: agents-and-tool-use

difficulty advanced. Scenario: an assistant books travel by searching, comparing and then booking. Steps: the loop: the model chooses an action, the app runs the tool, the result goes back in, repeat until done or a budget ends; why long tasks fail more (per-step success multiplies); the context grows every step so cost grows faster than steps; side effects and approvals; step, time and cost budgets; stop conditions; logging every step. Sources: Yao et al., "ReAct" (arXiv 2210.03629); Schick et al., "Toolformer" (arXiv 2302.04761). Related: `guardrails-and-prompt-injection`, `structured-output-and-function-calling`, `retries-and-backoff`, `idempotency`; link the case study `ai-agent-orchestration-platform` via related text, not a copy.
**Code (yes):** a scripted fake model and two tools (`search`, `book`) with a step budget of 5; print `step N: action -> observation` and the final result; include one step where the budget stops the run in a second scenario. **Playground:** controls `Steps in the task` (1 to 20, default 8), `Success of each step` (80 to 100 percent, default 95), `Check and retry each step` select (No, Yes with 1 retry; default No), `Tokens added per step` (default 500); outputs: chance the whole task succeeds (`r^n`; with one retry per step `(1-(1-r)^2)^n`), tokens processed in total when the whole history is re-read each step (`t x n x (n + 1) / 2`), and a verdict.

### Task 15: vector-index-internals

difficulty advanced. Scenario: nearest-neighbour search over 100 million vectors must answer in milliseconds. Steps: exact search compares the query to every vector (N x d work); IVF groups vectors around centroids and searches only the closest few lists (`nprobe`); HNSW is a layered graph that you walk toward the query greedily; product quantization splits each vector into m parts and stores one byte per part, shrinking 128 floats (512 bytes) to 16 bytes; the recall, speed and memory trade-off and the knobs. Sources: Malkov and Yashunin, "Efficient and robust approximate nearest neighbor search using Hierarchical Navigable Small World graphs" (arXiv 1603.09320); Jegou, Douze and Schmid, "Product Quantization for Nearest Neighbor Search" (IEEE TPAMI 2011; find a stable https url and test it). Related: `embeddings-and-vector-search`, `lsm-trees-vs-b-trees`, `distributed-search-scatter-gather`; link the `vector-database` case study from its page, not a copy.
**Code (yes):** 12 fixed 2-D points in 3 hand-placed clusters with centroids given; exact nearest neighbour for a fixed query, then IVF with `nprobe` 1 and 2, printing the candidates examined and whether the answer matched the exact one. **Playground:** controls `Vectors` select (1e6, 1e7, 1e8; default 1e7), `Dimensions` (128), `Index` select (Exact scan, IVF, IVF + product quantization), `Lists probed` (default 8); outputs: memory (float32 `N x d x 4` bytes in GB; PQ with m = 16 uses `N x 16` bytes), distance computations per query (exact `N`; IVF with `sqrt(N)` lists `sqrt(N) + nprobe x N / sqrt(N)`), and the note that approximate indexes can miss the true nearest neighbour.

### Task 16: training-serving-skew

difficulty intermediate. Scenario: a fraud model scores well offline and badly in production. Sources: Sculley et al., "Hidden Technical Debt in Machine Learning Systems" (NeurIPS 2015; find the https url and test it); Zinkevich, "Rules of Machine Learning" (developers.google.com/machine-learning/guides/rules-of-ml). Related: `model-evaluation-and-drift`, `slowly-changing-dimensions`, `pipeline-orchestration`; mention the `feature-store` case study from its page.
**Code (yes):** one feature, `days_since_signup`, computed by a "training" function (whole days between dates) and a "serving" function (rounds up) on 5 fixed dates; print each pair, the mismatches and the mismatch rate. **Playground:** controls `Features` (10 to 200, default 50), `Computed in two places` (0 to 100 percent, default 40), `Chance a second copy differs` (0 to 20 percent, default 5); outputs: features computed twice, expected differing features (`features x share x chance`), and the rule that a shared definition cuts it to 0. State that the chance is yours to set.
